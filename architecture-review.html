Strong

Data Model Fragmentation

Three different contact representations with manual transformation logic

High Impact

Files Involved

packages/types/src/contact.ts
apps/backend/database.py:77-110
apps/mobile/src/db/schema.ts
apps/backend/api_routes.py:73-135 (format_contact function)

Problem

Three different data models don't align, forcing complex transformation logic in format_contact(). Frontend has clean domain model, backend has legacy model, mobile has simplified sync model.

Interface ≈ Implementation: Each layer's data model is its implementation detail. Changes to Contact schema require updating transformation logic across 3+ files.

Solution

Create unified data contract (OpenAPI/GraphQL schema) shared across all layers. Introduce ContactDataAdapter interface that transforms between unified contract and each layer's storage format.

Deep Module Created: Simple interface (ContactDataAdapter.transformToStorage()), complex implementation hiding transformation logic.

Benefits

  • ✓ Improved locality: Contact schema changes isolated to adapter implementations
  • ✓ Testability: Transformation logic can be unit tested independently
  • ✓ Leverage: New storage backends (MongoDB, Redis) can be added without touching business logic
  • ✓ Deletion test: Deleting format_contact() would concentrate complexity into adapter

Scoring Engine Bypass

Backend uses hardcoded logic instead of shared scoring package

Medium Impact

Files Involved

packages/scoring/src/score.ts:43-49
apps/backend/api_routes.py:420-429
apps/backend/api_routes.py:74-84

Problem

Backend has duplicate hardcoded scoring logic that could drift from TypeScript implementation. The scoring package has clean interfaces but backend bypasses them.

No leverage: Scoring package exists but isn't leveraged by backend. Interface exists but implementation is duplicated.

Solution

Extract scoring as a shared service (TypeScript/Node.js microservice or Python port). Backend calls scoring service instead of duplicating logic.

Seam created: Backend depends on scoring service interface, not implementation. Scoring rules can be updated without redeploying backend.

Benefits

  • ✓ Single source of truth: Scoring logic defined once, used everywhere
  • ✓ Test surface: Scoring service can be tested independently
  • ✓ Deployment flexibility: Scoring can be deployed as edge function, microservice, or library
Speculative

Mobile Sync Tight Coupling

Mobile sync engine makes direct HTTP calls instead of using shared API client

Payoff depends on test needs

Files Involved

apps/mobile/src/sync/engine.ts:27-33
packages/api/src/client.ts
packages/api/src/interface.ts

Problem

Sync engine is tightly coupled to HTTP transport and endpoint structure. Cannot be tested without network, violates dependency injection principles.

No test surface: Sync engine can only be tested with real network calls. Interface ≈ Implementation (hardcoded URLs).

Solution

Refactor sync engine to use shared ApiClient abstraction. Inject API client dependency for testability.

Testable seam: Sync logic can be tested with mock API client. Transport details hidden behind interface.

Benefits

  • ✓ Unit testable: Sync logic can be tested without network
  • ✓ Transport flexibility: Could switch to WebSockets, Bluetooth, etc.
  • ✓ Shared abstraction: Admin app and mobile use same API client

Methodology

This analysis follows the deep module architecture principles:

Deletion Test

Would deleting this module concentrate complexity or just move it? A "yes" indicates shallow module.

Interface = Test Surface

A good interface makes testing easy. If testing requires mocking implementation details, the module is shallow.

One Adapter = Seam

One adapter creates a hypothetical seam. Two adapters make it real. We look for places where adapters would help.
